# PatchUp: unified photo privacy and storage update

Baseline: main-branch ZIP, commit 376198d71f39d54d600e572ccb8fa664f479b9a8. This is a single cumulative code change, not a live migration. Keep Gmail delivery disabled. Keep automatic AI acceptance off until a new held-out benchmark passes.

## Data flow and guarantees

- Original file is processed in the browser. `exifr.gps` reads latitude/longitude only. Canvas re-encodes image pixels. Original file, full EXIF, original name, capture time and device identifiers are not uploaded. Browser GPS is one-shot only for the live in-app camera; native OS camera/file selection is treated as potentially old gallery content. A photo without GPS needs a manually placed pin, unless the user explicitly requests current GPS while at the pothole.
- Before upload, inspect the preview for faces, plates, addresses or other personal details. The center-crop button removes 10% from each edge and can be repeated. Replace/retake if sensitive details remain. This is a manual privacy screen, not an automatic face/plate detector or guarantee of pixel anonymity.
- New authenticated `/api/media/upload` requires account consent, privacy confirmation and bounded image bytes. No direct client writes to `mediaObjects`. Sharp/libvips decodes, flattens, limits pixels, strips source metadata and emits new JPEGs. No original image containers retained. Thumbnail <=320 px and <=40 KB. Evidence max 1280px/400KB server; browser targets 960px/300KiB with 720px fallback. Do not lower quality without evaluation. HEIC is rejected with JPEG export instructions; no HEIC decoder included.
- Gemini's actual request builder independently decodes and re-encodes the input, uses inline JPEG bytes + fixed ATLDOT prompt + fixed schema. No EXIF, notes, account identifier, filename, or GPS field is in the request. Real EXIF GPS/XMP fixtures test that boundary. The API may still infer locations from visible landmarks and receives ordinary network/service metadata; this is not zero retention or anonymization. Paid-mode setting is an operator attestation; verify the linked billing account and key before enabling it. Disable optional provider data-sharing. No real community photos on unpaid Gemini. Restrict pilot to adults; self-attestation is not independent age verification.
- User confirms the pothole pin and independently sourced street name before publication. EXIF or device GPS is an estimate, not proof; users may correct it. Manual street labels are from signs/own knowledge, not copied from Google Maps. Optional city centerline lookup is disabled until data use rights, endpoint/ownership fields and availability are verified. It sends the selected coordinates to the city service, not Gemini; no account identity is sent to that service. Unknown road ownership is marked for admin review, and may produce an internal five-pothole draft, not a city submission. Existing legacy reports show warnings requiring independent street/jurisdiction verification. State routes are not automatically assumed City-owned. The geographic bounding box is not the city boundary.
- Existing canonical documents retain private owner/notes/accuracy/provenance for the user's gallery, moderation and claims. Public map, gallery/evidence and activity endpoints expose allowlisted anonymous data rather than raw records. Public community photos still show pothole coordinates and may reveal location in pixels. Friend-specific map/feed filters removed to avoid exposing travel history. Own gallery and My Spots still work. Public map now refreshes every 30 seconds with short server cache; admin queues and private submissions remain protected. Approved media can be retrieved without auth via the server, with 2-minute private browser caching; private media uses owner/admin auth and no-store. Do not publish direct object URLs. Avatar uploads have a separate public-sharing confirmation; they are not sent to Gemini.
- Existing legacy photo bytes are not eligible for new AI checks; display path sanitizes at request time. Existing pending reviews remain reviewable and are excluded from migration until resolved. Existing contributor identities in stored canonical records remain private after rules rollout. Old copies/downloads outside PatchUp cannot be recalled. Legacy photos and street labels need independent human review before export or sending to ATL311. Privacy notice `/privacy.html` is a starting point: publish actual team support/contact details and review it with the case-study owner.

Keep raw files out of the bucket.
3. Grant the existing backend service account minimum necessary object permissions on this dedicated bucket only (read/create/delete for migration/retention; bucket metadata access only if necessary). No browser service-account keys. Deploy Storage rules to the intended dedicated Firebase bucket (not a shared unrelated bucket). Admin SDK is authorized via IAM, not Firebase client rules.
4. Set Render environment: `PATCHUP_MEDIA_STORAGE=firestore` initially for staging if bucket is not ready; for new GCS writes set `PATCHUP_MEDIA_STORAGE=gcs` and `PATCHUP_MEDIA_BUCKET=<actual bucket>`. Existing records keep their backend pointer; both stores are readable. `PATCHUP_MEDIA_BUCKET` must remain configured to read older GCS-backed records even if new uploads switch to Firestore. Missing/wrong bucket fails closed. Keep account consent version migration and new frontend/rules in sync: stop old uploads, deploy tighter Firestore rules/indexes and new code during a maintenance window, force old browser/PWA sessions to reload. Do not automatically deploy rules to production from a test command.
5. Recommended initial caps: AI 10/user/day, 100/day global, 1000/month, 10/minute; uploads 10/user/day, 100/day global, 1000/month; new allocation cap 250 MB Firestore or 3 GB GCS, cumulatively counted. Set existing Render env overrides to these values explicitly; .env.example does not alter deployed env. Quotas reserve before writes/provider calls and can conservatively count failed requests. Caps are not total storage or hard billing caps: legacy/migration bytes, soft-deleted objects, read traffic, network transfer, Google Maps, and other project usage are not counted. Never reset counters casually. Monitor actual bucket bytes and provider usage. At 1000 photos/month, two objects per photo = 2000 base object creates, before verification/migration/other operations. Paid AI example 1500 input and 100 output tokens per photo at $0.30/M and $2.50/M = $0.70 per 1000 classifications (illustrative, verify pricing and actual usage).
6. No Gmail delivery is enabled by this update. Coordinates in internal email drafts are exact confirmed pothole positions, not EXIF metadata; photos fetched via protected routes and rendered as JPEG. Do not send until street, jurisdiction, pixels and city authorization are checked.

## Dry-run-first migration / rollback

Use Node 24, installed dependencies, explicit target project and **named** database from the local configuration, and authorized staging credentials. Do not paste credentials into agent output. Use the command below with actual staging identifiers; do not use production IDs for a test. A dry run reads the database and may incur small read costs; it does not write. `--after` is the opaque last document ID printed as `nextCursor`. Repeat in bounded batches (max 50). Preserve a backup before changes. Pause uploads, reviews and account deletion during apply/prune. Do not run concurrently with app writes.

```sh
npm run media:migrate -- --project <project> --database <database> --target gcs --limit 25
npm run media:migrate -- --project <project> --database <database> --target gcs --limit 25 --apply --maintenance-window
```

The script migrates accepted retained evidence/profile pictures after decoding and checking, preserving stable IDs/URLs and old claim aliases. GCS objects are immutable hash-keyed JPEGs with generation, size and SHA-256 verified before the Firestore pointer changes. Sanitized Firestore copies retained for rollback. Pending reviews are skipped. Unreferenced legacy images are scheduled for conservative seven-day cleanup during apply. Invalid or changed records are skipped and reported; reconcile before proceeding. Migration is bounded and restartable but Firestore and Storage are not one atomic transaction: a crash can leave objects uploaded before a pointer update. Rerun in a maintenance window, verify hashes, and audit orphan objects against live pointers before manual deletion. Never bulk-delete a bucket prefix. Test migrated gallery, map and draft attachments and confirm no pending review was changed.

After verification and backups, use `--target prune` to verify both GCS variants and remove Firestore copies (with same apply flags). Rollback via `--target firestore` reads GCS bytes, verifies hashes, restores canonical Firestore bytes and changes the pointer. Keep GCS configured until no pointers remain. Rollback preserves verified images, not old unsanitized metadata. GCS copies from rollback remain until explicitly audited and retired; don't delete them blindly. Migration does not rewrite legacy Google-derived street labels or scrub visible personal details. Review legacy locations and photo contents before public launch; remove unnecessary legacy cached addresses through a separately reviewed data repair. Do not publish old data externally based solely on a legacy report.

## Cleanup

New abandoned upload deadline 24h; rejected review 7 days; unresolved reviews and accepted evidence retained; avatars checked periodically. `PATCHUP_MEDIA_MAINTENANCE_ENABLED=true` runs an hourly sweep while server is active and on startup. Render Free sleeps, so no guaranteed 24-hour execution. Admin-only `POST /api/admin/media-maintenance` or `npm run media:migrate -- --project ... --database ... --target maintenance --apply --maintenance-window` executes bounded cleanup explicitly. For guaranteed scheduling use a separately authenticated scheduler/worker once approved; no external scheduler was provisioned. Object tombstones allow later retries. Cleanup preserves claims and accepted photos, anonymizes account-deleted contributor IDs, removes notes and private user verification data. Legacy originals may exist until migration. Deletion does not undo earlier public downloads or provider processing.
